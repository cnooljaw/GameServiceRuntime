# GSR 设计决策索引

本文提供长期设计记忆的检索入口，帮助回答“为什么这样设计”。它不定义公开 API，也不替代 RFC；每项结论的完整边界、失败语义和验收条件均以链接的 RFC 为准。

## 使用方式

1. 先按关键词找到相关决策。
2. 阅读“权威来源”中的 RFC，而不是只根据本页摘要修改代码。
3. 若结论影响当前 Phase，再阅读路线图和实现测试。
4. 新结论先写入 RFC，再更新本索引。不要只留在聊天记录、`AGENTS.md` 或 Skill 中。

## 运行时模型

| 决策 | 结论 | 原因摘要 | 权威来源 |
| --- | --- | --- | --- |
| D-001：使用 Service，而非 Actor | GSR 使用 `Service`、`ServiceRef`、`Command`、`Send`、`Call`，不引入 Actor 术语或模型。 | 运行时要表达可寻址状态、Mailbox 串行和显式生命周期，不把框架误解为 Erlang/OTP 的 Actor Tree。 | [术语表](rfcs/RFC-0000-Foundation-Glossary.md)、[设计原则](rfcs/RFC-0001-Foundation-Design-Principles.md) |
| D-002：Core 与业务解耦 | Core 只提供通用运行语义；Tooling 提供工程策略；Business Layer 持有游戏领域状态。 | 让 Runtime 保持可组合、可测试，避免为单一业务或 adapter 扩张内核。 | [设计原则](rfcs/RFC-0001-Foundation-Design-Principles.md)、[冲突裁决](rfcs/RFC-0002-Foundation-Conflict-Resolution.md) |
| D-003：状态只经 Mailbox 变化 | Service 的业务状态只在 Command handler 中修改；跨 Service 只传 `ServiceRef` 与 Command。 | 保持单一状态 owner 与可推理的串行边界，避免对象指针、多锁和旁路状态。 | [Service](rfcs/RFC-0100-Core-Service.md)、[Mailbox](rfcs/RFC-0150-Core-Mailbox.md) |
| D-004：异步必须有 owner | Service 默认不创建 goroutine；Timer 只投递 Command；例外任务必须有生命周期 owner、关闭入口和真实返回追踪。 | 防止 Handler 外状态竞争、关闭泄漏和看似超时却仍在运行的任务。 | [设计原则](rfcs/RFC-0001-Foundation-Design-Principles.md)、[生命周期](rfcs/RFC-0180-Core-Lifecycle.md) |
| D-005：Timer 不是 Service | Timer 是 Core 的未来 Command 投递能力，不执行回调；不把 Timer Wheel 设计成 Service。 | 定时不应绕过 Mailbox，也不应增加没有独立状态或地址价值的运行单元。 | [Timer](rfcs/RFC-0170-Core-Timer.md) |
| D-006：不引入 `SystemServiceID` | 系统 Service 与普通 Service 一样使用动态 `ServiceID` 和稳定 `ServiceName`；只有 `ServiceID(0)` 保留给 Core 节点端点。 | 避免魔法实例 ID 与部署配置耦合，区分实例地址、长期名字和 Runtime 自身的节点级协议。 | [ServiceRef 与寻址](rfcs/RFC-0110-Core-ServiceRef.md) |
| D-021：Handle 是唯一 Command 分发入口 | Runtime 不要求 Service 声明 Command 清单，也不维护 per-Service Command 白名单；未知 Command 进入 Mailbox 后由 Handler 返回错误。 | `CreateService` 与 `Handle` 已完成入口绑定。额外清单重复表达 Handler 能力，并把转发负担扩散到 Decorator；Skynet 同样把业务 `CMD` 表留在 Service 内部。 | [Service](rfcs/RFC-0100-Core-Service.md)、[Command](rfcs/RFC-0120-Core-Command.md) |

## Cluster 与 Tooling

| 决策 | 结论 | 原因摘要 | 权威来源 |
| --- | --- | --- | --- |
| D-007：`ResolveRemote` 只做节点级查询 | 已知节点上的长期名字通过 `Runtime.ResolveRemote` 查询其本地实例；它不是全局目录或路由 API。 | 静态 bootstrap 与动态发现分层，避免把节点级能力膨胀为控制面。 | [Cluster Data Plane](rfcs/RFC-0190-Core-Cluster-Data-Plane.md)、[Discovery](rfcs/RFC-0200-Tooling-Discovery.md) |
| D-008：Discovery 属于 Tooling，且不做 Gossip | Discovery 保存节点 lease 和长期 ServiceName；不保存 ServiceGroup、不决定路由、不复制为 Gossip。 | 第一版先提供单一、可验证的权威事实，避免选主、一致性和传播协议过早进入 Runtime。 | [Discovery](rfcs/RFC-0200-Tooling-Discovery.md) |
| D-009：Supervisor 是可选恢复策略 | Runtime 负责实例 Create/Stop；`Supervisor` 只在真正承担失败监控、恢复预算和重启策略时作为 Tooling 存在，不是 Core 生命周期替身或 OTP Tree。 | 避免承诺不存在的自动恢复语义，同时允许对已定义的 panic 失败路径做受限恢复。 | [Supervisor](rfcs/RFC-0220-Tooling-Supervisor.md) |
| D-010：Observed State 先于 Desired State | Discovery、NodeAgent、Observer 只描述当前事实；Controller 负责 Desired State 与 Reconcile，NodeAgent 只执行动作。 | 将“看见系统”与“改变系统”的权限、失败处理和策略分开，防止只读观测面悄然变成运维控制面。 | [Control Plane](rfcs/RFC-0250-Tooling-Cluster-Control-Plane.md)、[Drain 与热更新](rfcs/RFC-0270-Tooling-Drain-Hot-Reload.md)、[路线图](rfcs/RFC-0500-Roadmap.md) |
| D-011：ServiceGroup 独立于 Discovery | `DirectoryService` 是 ServiceSet 的唯一事实 owner；Router 只使用调用方显式持有的快照。 | 避免 Discovery 兼任目录和负载策略，也避免看似异步的 Send 隐含同步远程查询或后台缓存。 | [ServiceGroup](rfcs/RFC-0260-Tooling-ServiceGroup-Routing.md) |
| D-012：Drain 使用入口 guard、版本切换与访问者 lease | Drain Guard 在旧实例自己的 Mailbox 内拒绝显式外部 Command；受控操作在新实例就绪后发布更高 ServiceSet，再等待 VisitorRegistryService 的强 lease 清零，最后才 Stop。Guard 开始后不得重新发布原旧 Ref；恢复需新实例和更高版本。 | 热更新不是进程内代码补丁，缓存旧 ServiceRef 不能只靠切流阻止；不可逆 Guard 使“原 Ref 回滚”不再成立，访问关系不能散落在调用方共享 map，更不能污染 Core 最小接口。 | [Drain 与热更新](rfcs/RFC-0270-Tooling-Drain-Hot-Reload.md)、[Drain Guard](rfcs/RFC-0271-Tooling-Drain-Guard.md)、[受控 Drain 操作](rfcs/RFC-0272-Tooling-Controlled-Drain-Operation.md) |

## 演进与协作

| 决策 | 结论 | 原因摘要 | 权威来源 |
| --- | --- | --- | --- |
| D-013：分阶段只引入一个核心问题 | Phase 10A 先冻结 Visitor lease，Phase 10B 再独立交付入口 Drain Guard；ServiceSet 切换、回滚、Desired State、Controller、Reconcile 与修改型 NodeAgent 动作进入后续带操作身份的契约。 | 将复杂度拆成可验收的能力，避免把自动恢复、调度和策略塞入 Discovery 或 Core，也不让无审计的 decorator 承担未知提交恢复。 | [路线图](rfcs/RFC-0500-Roadmap.md)、[Drain 与热更新](rfcs/RFC-0270-Tooling-Drain-Hot-Reload.md)、[Drain Guard](rfcs/RFC-0271-Tooling-Drain-Guard.md) |
| D-014：聊天结论必须回写 | 聊天用于探索；稳定结论先进入 RFC，再进入本索引，最后按需同步路线图、`AGENTS.md` 和 Skill。 | 让归档后的设计理由仍可检索，避免后续实现靠重新推理或误读历史上下文。 | [RFC 生命周期](rfcs/RFC-0003-Foundation-RFC-Lifecycle.md)、[Codex 开发指南](GSR-Book/06-第六篇-实践/02-Codex开发指南.md) |
| D-015：修改型 Drain 先保存操作事实 | Phase 10C1 的 Coordinator 以 Gateway source、Principal 与 RequestID 约束 Start/Resolve，并保存 Directory/Guard/Visitor 的未知或已确认阶段；它只到 ReadyToStop。 | 超时不能证明 Publish 或 Begin 未发生，且 Runtime.Stop 需要节点级生命周期 owner；把操作事实、动作授权和执行 Stop 分开，才能避免脚本式重试破坏版本或重新接流被 Guard 的旧 Ref。 | [受控 Drain 操作](rfcs/RFC-0272-Tooling-Controlled-Drain-Operation.md) |
| D-016：Stop 由节点外部 Runner 执行 | Coordinator 只授权、复核 Directory 并记录 StopOperation；NodeAgent 保存本地 receipt；组合根持有的有界 Runner 才调用 Runtime.Stop。 | Service Handler 直接 Stop 会把 Runtime 生命周期与 Mailbox 执行许可耦合，可能在单 worker 下无法调度目标 Stop；将阻塞生命周期调用放到可关闭、等待真实返回的外部 adapter，结果再经 Command 回到状态 owner。 | [受控 Node Stop](rfcs/RFC-0273-Tooling-Node-Stop-Execution.md) |
| D-017：恢复只创建替代实例并由人工确认发布 | 已 Guard/Stopped 的旧 Ref 永不恢复；组合根的 Blueprint Runner 创建新 Ref，Coordinator 只在操作者 Confirm 后以 Directory CAS 发布更高 ServiceSet。 | Stop 后不存在可安全逆转的 Guard/生命周期事务；把创建 factory 或自动补偿塞进 Coordinator 会混淆 Runtime owner、业务放置与审计责任。 | [人工恢复与补偿](rfcs/RFC-0274-Tooling-Manual-Recovery-Compensation.md) |
| D-018：录制在 Handle 边界、持久化在 Service 外 | Decorator 记录可编码 Command 到有界 RecorderService；Archive 文件/对象存储由外部 adapter 导出，录制默认不阻断业务。 | Core 不应增加可变 Envelope hook；把文件 I/O 放进目标 Handler 会破坏 Mailbox 延迟和关闭语义。 | [Command Record 与 Replay](rfcs/RFC-0280-Tooling-Command-Record-Replay.md) |
| D-019：Wallet 用异步 ledger result 收敛 | Wallet Mailbox 保存 RequestID 状态；组合根的 LedgerRunner 调用可恢复 Store，结果以私有 Command 回到 Wallet，再通知 Battle。 | Snapshot/定期 Backup 不能成为资金事实；Handler 直接 I/O 或超时即拒绝会制造不一致与重复记账。 | [WalletService](rfcs/RFC-0360-Business-WalletService.md) |
| D-020：业务层直接使用 Command 原语 | 业务调用者按是否需要当前结果选择 `Send` 或 `Call`；Handler 直接 Reply，Send 到达时 Reply 成功无副作用。BattleContext/PlayerContext 只补充当前 Handler 的领域能力，不包装成另一套 RPC；Room/Wallet 保持直接 Handler。 | 学习 Skynet 的明确 Service 职责与消息原语，同时以 Go 的 Context 有效期和 Mailbox 串行保证防止 Handler 外并发。 | [Business Layer](rfcs/RFC-0300-Business-Layering.md)、[Battle](rfcs/RFC-0310-Business-Battle.md)、[PlayerModule](rfcs/RFC-0350-Business-PlayerModule.md)、[业务模板](rfcs/RFC-0370-Business-Templates.md) |
| D-022：战斗编号由协调者循环分配 | `BattleID` 冻结为 `uint32`，`0` 无效；协调者编号池默认范围为 `1..10000`，上限可配置。创建调用方分配编号，Host 只创建实例并返回 `BattleRef`。第一阶段直接使用旧 GM 的数值 `GameInnerId`，不做字符串转换。BattleID 只在活动集合内唯一，实例完全结束后可以回收；同一编号的新实例使用新的完整 `BattleRef`。普通创建拒绝活动编号冲突；旧 GameLogic 的同号覆盖只作为 Legacy bridge 的异常兼容流程保留。后续 GSR GameMaster 继续承担编号分配与回收。 | `BattleID` 表达当前战斗编号，不是永久记录 ID；完整 `BattleRef` 表达运行实例并隔离编号复用后的迟到消息。该边界避免 Legacy bridge 维护第二套映射，也避免 Host 同时承担编号策略和实例生命周期。 | [Battle](rfcs/RFC-0310-Business-Battle.md)、[路线图](rfcs/RFC-0500-Roadmap.md) |
| D-023：复用 BattleID，不复用 ServiceRef | 每局动态创建新的 BattleService 和 ServiceRef，结束后经外部生命周期 runner Stop；Host 用 `MaxActiveBattles` 限制同时活动实例。编号回收后创建同号 Battle 仍获得新的完整 Ref。第一阶段不预创建固定 Service 池；累计创建压力由 churn 测试和 benchmark 验证。 | ServiceRef 是当前节点进程内的 `{NodeID, ServiceID}` 运行地址，不是内存地址。Stop 会清理 Registry、Timer、PendingCall 和 Mailbox；同一 Runtime 进程内 ServiceID 单调分配且不复用。容量上限已经约束活动内存，固定池不能替代生命周期泄漏修复。 | [ServiceRef 与寻址](rfcs/RFC-0110-Core-ServiceRef.md)、[生命周期](rfcs/RFC-0180-Core-Lifecycle.md)、[Battle](rfcs/RFC-0310-Business-Battle.md)、[路线图](rfcs/RFC-0500-Roadmap.md) |
| D-024：程序缺陷按 Battle 隔离取证 | 普通 Handler 或 Timer Handler 的 panic、不变量失败和 Handler/Stop 超时只使对应 Battle 进入 `Quarantined`，保留编号并拒绝该 Battle 的流量。Timer Handler 不得像参考实现一样只记录 panic 后返回。GM 连接随后断开、`DEL_GAME` 或同号 `NewGame` 都不覆盖隔离状态，不自动 Stop、替换或释放该 Battle；它继续占用容量，只能按诊断 receipt 局部释放。其他 Battle 和 GM 连接继续运行，节点报告 `Degraded`，不因单 Battle 缺陷整体回切。不同编号的新局在容量内仍可创建；Host 以 `Creating + Active + Stopping + Quarantined` 计算占用。最后稳定 Snapshot、输入 Record、随机种子、Clock、失败 Command、Command Record Sequence、TurnRevision、TimelineRevision、stack 和 Runtime Inspection 由外部诊断 runner 导出；确认取证前不自动 Stop、重建或释放。取证后以 ID、完整 Ref 和诊断 receipt 局部释放，代码修复后正常上线。 | 吞掉 Timer panic 会让牌局继续停留在可能只更新了一半的状态；自动清理又会销毁现场。按 Battle 隔离把影响限定在故障实例，同时保留确定性重放证据。后续正常协议消息不应把程序缺陷伪装成普通生命周期结束。Runtime panic 后对象未必仍可访问，因此诊断以稳定副本和输入事实为准。 | [Record 与 Replay](rfcs/RFC-0280-Tooling-Command-Record-Replay.md)、[Battle](rfcs/RFC-0310-Business-Battle.md)、[路线图](rfcs/RFC-0500-Roadmap.md) |
| D-025：业务 Timeline 决定牌局进展期限 | Host 不设置最长牌局时间、最后进展扫描或通用停滞 Watchdog。具体玩法配置自己的出牌、托管、结算和结束期限，并通过 Battle Timeline 投递带 Timeline Revision 的 Command；单纯运行时间长不触发隔离。宁海双扣首版只调度参考生产路径实际启动的 Timer；没有启动点的 `Deal`、`ContinueDelay` 不主动调度，未被使用的 timer-key 参数不公开，只有枚举和取消调用的 `TimerGameOver` 不实现。 | 时间规则属于玩法状态机。Host 级超时既无法区分合法长局与缺陷，也会形成绕过 Mailbox 的第二套生命周期判断。Core Timer 已绑定完整 ServiceRef，Timeline Revision 保持同实例内的取消/替换 fencing；明确投递或处理错误才进入诊断。没有真实调用证据的定义不应膨胀公开契约。 | [Timeline](rfcs/RFC-0320-Business-Timeline.md)、[路线图](rfcs/RFC-0500-Roadmap.md) |
| D-026：一次出牌机会只有一个行动期限 | 宁海双扣每个 `TurnRevision` 只保留一个有效的 `ActionDeadline`。普通玩家使用 `MsFirstOutCard`/`MsOutCard` 并产生 `AskRespTimeOut`；托管/机器人在 `MsOutCardRobot > 0` 时使用专用期限并产生 `AskRespAuto`，否则回退到普通期限与 `AskRespTimeOut`；外部 AI 在 `MsAITimeout > 0` 时使用硬期限并产生 `AskRespAITimeOut`，否则同样回退。有效 AI 结果到达后，真实机器人立即以 `AskRespAI` 完成；离线托管玩家若尚未达到 `MsOutCardRobot` 最小延迟，则先取消硬期限，再以剩余延迟替换为唯一的 `ActionDeadline`，到期应用已保存候选。不得同时保留硬期限与最小延迟 Timer，也不得像参考实现一样并行启动 `OutCard` 与 `OutCardRobot`/`OutCardAI`。玩家响应、AI 完成、当前期限到期或回合推进都会使旧 Timeline Revision 失效；只有回合推进才更换 `TurnRevision`。 | 参考实现的双 Timer 把多个可执行业务动作并行留在同一回合，调度顺序会改变结果；但旧 BaseGame 对离线托管 AI 确实保留 `MsOutCardRobot` 最小可见延迟。用期限替换而不是新增并行 Timer，可以兼容该节奏，同时维持一个明确的下一业务动作。 | [Timeline](rfcs/RFC-0320-Business-Timeline.md)、[路线图](rfcs/RFC-0500-Roadmap.md) |
