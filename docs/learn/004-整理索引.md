# Skynet 到 GSR 设计整理索引

本文档组来自 `docs/learn/go-skynet-chatgpt-20260708-1207.md` 的二次整理。

## 状态说明

`docs/learn/` 是学习、推导和历史整理材料，不再作为最终实现依据。

正式设计以 `docs/rfcs/` 为准。如果 `docs/learn/` 与 `docs/rfcs/` 冲突，必须采用 RFC 结论。

已知历史口径包括：

- `learn` 中的两层分层 `Core Runtime / Game Layer` 已被 RFC 的三层结构取代：`Core Runtime / Runtime Tooling / Business Layer`。
- `learn` 中对 Gateway 的描述较粗，现以 RFC 中的 `Gateway Adapter / ProtocolMapper` 边界为准。
- `learn` 中 Stop 流程较简化，现以 RFC-0180 的 `Stop(ctx)`、`Close()`、超时和强制关闭规则为准。
- `learn` 中实现阶段顺序较早，现以 RFC-0500 的路线图为准。

整理原则：

1. 越靠后的聊天内容置信度越高。
2. 被后续推翻的命名不再作为最终结论。
3. 原始聊天和整理文件用于追溯设计演进，不替代 RFC。
4. 正文使用中文，API、类型名、目录名保留英文。

## 最终稳定术语

| 最终术语 | 废弃或低置信度术语 | 说明 |
|-|-|-|
| Service | Actor | Actor 只作为思想背景，不作为项目命名。 |
| ServiceRef | ActorRef、对象指针 | ServiceRef 是地址，不是对象引用。 |
| CreateService | Spawn、Boot | 创建由 Runtime 管理生命周期。 |
| Call | Request、Ask | 最终采用 `Call`，贴近 Skynet 的 `call` 语义。 |
| Send | Tell | 异步投递，不等待业务结果。 |
| Command | Event、RPC Command | Command 是 Service 能力入口，不是 DDD/CQRS Command。 |
| Battle | Attack | Battle 表示游戏对局，Attack 只是动作。 |
| Timeline | TickLoop | Timeline 表示游戏时间轴。 |
| Cluster Transport | RPC、gRPC Stub | Cluster 是远程消息管道，不是传统 RPC。 |
