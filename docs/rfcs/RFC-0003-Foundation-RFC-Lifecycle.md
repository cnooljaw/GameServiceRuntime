# RFC-0003：RFC 生命周期与写作规范

> 状态：已接受  
> 范围：`docs/rfcs/`  
> 依据：[RFC-0002](RFC-0002-Foundation-Conflict-Resolution.md)

## 目的

本文定义 GSR RFC 的状态、最小结构和验收规则。它帮助维护者区分“已经裁决的设计”“尚未实现的计划”和“已经由代码验证的公开契约”。

## 权威顺序

发生冲突时，按以下顺序裁决：

1. 已接受 RFC。
2. Skynet 的设计规则。
3. Skynet 源码表现出的真实约束。
4. Go 惯例和一般工程规则。

实现与已接受 RFC 冲突时，先修改 RFC 并记录裁决，再修改代码。草案和待实现 RFC 不能推翻已接受 RFC；如确需改变既有公开行为，必须同时给出兼容性和迁移说明。

## 状态

RFC 只使用以下状态：

| 状态 | 含义 | 是否可作为实现验收依据 |
|---|---|---|
| 草案 | 仍有影响接口、所有权或失败语义的开放问题。 | 否。 |
| 待实现 | 设计已审查，可以据此编写实施计划，但代码尚未完成。 | 是。 |
| 已接受 | 实现、测试和文档已经通过验收；公开契约生效。 | 是。 |
| 已废弃 | 契约不再适用，并明确指向替代 RFC 或删除原因。 | 否。 |

路线图属于持续维护文档，使用“已接受”状态，并在“当前执行状态”中记录更新时间和下一阶段。

## 元数据

每份 RFC 的 H1 后必须依次写明：

```markdown
> 状态：草案 | 待实现 | 已接受 | 已废弃  
> 目标阶段：Phase N（基础约定和已实现 Core RFC 可省略）  
> 范围：Core Runtime | Runtime Tooling | Business Layer | Examples  
> 依赖：链接到直接依赖的 RFC；没有依赖时写“无”
```

“依据”只用于记录参考资料，不能代替“依赖”。聊天记录和学习笔记不是公开契约。

## 必备章节

可实现 RFC 至少包含：

1. `目的`：本文帮助读者决定或实现什么。
2. `目标`：本阶段必须交付的行为。
3. `非目标`：明确留在后续阶段或外层 adapter 的能力。
4. `分层与依赖`：owner、依赖方向和禁止反向引用。
5. `公开契约`：类型、方法、Command、稳定字段或协议。
6. `状态与生命周期`：状态由谁创建、修改、保存和清理。
7. `错误与失败语义`：稳定错误、重试、超时、迟到和部分成功。
8. `并发与所有权`：串行边界、goroutine owner、返回副本和锁约束。
9. `可观测性`：指标、日志或 Inspection 的责任边界。
10. `验收`：正常、重复、超时、取消、panic、关闭竞争和兼容性测试中适用的部分。

纯基础约定可以省略不适用的章节，但不能省略会改变裁决的问题。

## 规范用语

- “必须”“不得”表示实现和 Review 必须满足的约束。
- “应”“不应”表示默认规则；偏离时必须在实施计划中说明原因。
- “可以”表示兼容契约内的可选行为。
- “建议”“草案”不能用于定义稳定 API 或错误语义。

API 示例必须使用仓库术语和可落地的 Go 类型。未定义的类型要在同一 RFC 中说明 owner，不得用接口草案掩盖尚未裁决的生命周期问题。

## 分层规则

新增公开能力前必须先判断它属于 Core、Runtime Tooling 还是 Business Layer：

- Core 只接受多个上层共同需要、且无法在外层组合完成的通用运行语义。
- Runtime Tooling 通过窄接口消费 Core，不得要求 Core 引用 Tooling 类型。
- Business Layer 拥有领域状态、持久化策略和协议语义，不得把领域类型压入内层。

为单一 adapter 增加 Core getter、回调或 Registry 入口前，必须证明现有 `Command`、`ServiceRef`、`Runtime.Inspect()` 和组合 adapter 无法形成可靠测试缝。

## 接受流程

RFC 从“待实现”变为“已接受”前必须完成：

1. 失败测试先于可见行为实现。
2. 公开符号有 Go doc，返回值和零值语义明确。
3. RFC、代码、测试、README、路线图和示例不存在互相冲突的状态描述。
4. `go test ./...`、`go vet ./...`、`go test -race ./...` 通过。
5. 并发敏感能力执行针对性的重复测试。
6. Review 无未处理 P1/P2 问题。

“已接受”描述公开行为，不表示后续永远不能修改。兼容扩展可以直接修订；不兼容修改必须先写迁移说明，并进入新的 minor 版本。
