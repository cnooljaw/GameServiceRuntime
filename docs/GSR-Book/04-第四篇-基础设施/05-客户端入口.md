# 客户端入口

> 状态：已实现
>
> 公开契约：[RFC-0290](../../rfcs/RFC-0290-Tooling-LoginService-Gateway.md)

客户端带着账号、token 和二进制协议来到门口。Runtime 只认识 ServiceRef 和 Command。谁负责把两种世界接起来，又不让 secret、socket 和协议号进入 Core？

## 本章目标

理解客户端身份如何在不污染 Core Runtime 的前提下，从登录连接进入已认证业务 Command。

首版位于 `tooling/entry`，提供内存 `SessionRegistry`、`LoginService`、TCP Login Adapter、TCP Gateway Adapter 和业务 `ProtocolMapper` seam。

## 分工

```text
Handshake
  -> Login Adapter
  -> SessionRegistry.StoreSecret
  -> LoginService IssueTicket Command
  -> TicketIssue
  -> Gateway AUTH proof
  -> SessionRegistry.VerifyAndBind
  -> ProtocolMapper.Map
  -> Runtime Send / Call
```

- `Handshake` 负责具体 challenge、密钥协商和外部认证。GSR 只要求它返回已认证 identity、至少 32 字节 secret 和过期时间。
- Login Adapter 拥有登录连接任务。它存储 secret 后只向 LoginService 发送 `AuthIdentity`、`SecretRef` 和过期时间。
- LoginService 是一个普通 GSR Service。它在 Mailbox Handler 中执行 SingleSession 策略；重建后先从 Registry 读取当前 ticket，再继续递增 Generation。
- SessionRegistry 在私有同步边界内持有可按 `AccountID + Server` 恢复的当前 ticket、secret、proof 序号和当前连接绑定。它不是 Core Runtime，也不是业务状态 Service。
- Gateway Adapter 拥有游戏连接，认证成功后只把 `SessionIdentity` 与包交给 Business Layer 的 `ProtocolMapper`。

Core 不知道 socket、token、ticket、secret、proof、uid、subid 或客户端协议号。

## 代际和 proof

同一 `AccountID + Server` 的成功新登录产生更大的非零 Generation。SessionRegistry 原子撤销旧 ticket，并把旧 Gateway `ConnectionID` 交给组合根的 `ConnectionCloser` 关闭。Gateway 在每个业务包进入 mapper 前再次确认该 connection 仍是 Registry 的当前绑定，因此撤销提交后，旧连接即使尚未收到 socket close，也只能收到 `ERR session_revoked`，不能再投递新的业务 Command。旧 ticket、旧 proof 和迟到 `Unbind` 都不能重新影响新连接。

Gateway 首行固定为：

```text
AUTH <uid> <subid> <server> <generation> <sequence> <proof>\n
```

文本字段是无填充 base64url；数值是无前导零的十进制非零整数。proof 是对 RFC 固定 `GSR-Gateway-Proof-v1` 输入计算的 HMAC-SHA-256。`Sequence` 在一个 ticket 生命周期中严格递增，并在 Registry 的 `VerifyAndBind` 临界区内才被接受。因此并发重放最多成功一次。

登录成功响应为：

```text
TICKET <uid> <subid> <server> <generation> <expires_unix_ms>\n
```

这个响应不携带 `SecretRef` 或明文 secret。失败仅返回稳定 `ERR <code>`，不暴露认证、HMAC 或 Registry 的内部原因。

## ProtocolMapper seam

Gateway 不理解 `CmdJoinRoom`、`CmdAction` 等业务语义。Business Layer 实现：

```go
type ProtocolMapper interface {
    Map(entry.SessionIdentity, entry.ClientPacket) (entry.Route, error)
}
```

`Route` 指定目标 `ServiceRef`、`CommandID`、payload 和 `Send`/`Call` 方式。需要 Call 结果时，mapper 再实现 `CallResponseMapper`；它负责把业务结果编码成不含换行的客户端 payload，Gateway 只追加行结尾并写回。

这使连接协议变化停留在 mapper 和 Adapter，业务 Service 只接收已经认证的身份上下文与业务 payload。业务幂等仍由协议携带的 `RequestID` 负责，不能复用 Core `SessionID` 或 Gateway proof Sequence。

## 生命周期

Adapter 的 `Start` 由组合根调用。`Close(ctx)` 关闭 listener 和活动连接、取消 Handshake/Call context，并等待 accept 与所有连接任务真实返回。调用方 context 超时只结束等待，不会把仍在运行的任务伪装成已关闭。

Service 不直接创建 goroutine；Adapter 的连接 goroutine 不属于 Service，也由 Adapter 自己追踪。

Gateway 默认最多保留 `1024` 个连接。认证前和认证后的每次读都受 `30s` 空闲超时限制；每个已认证连接固定一秒内最多 `100` 个业务包。组合根可通过 `GatewayAdapterConfig` 收紧这些值。超过连接数、空闲超时和超过包率分别写 `ERR busy`、`ERR timeout` 和 `ERR rate_limited` 后关闭，业务 mapper 不会被调用。

Login Adapter 默认最多处理 `1024` 个连接；一次 `Handshake.Accept` 和 ticket 签发合计最多运行 `10s`。超过连接数或握手时限分别写 `ERR busy`、`ERR timeout` 后关闭。LoginService 读取的 TicketRegistry 必须是进程本地且非阻塞的，不能在 Mailbox Handler 内做远程或持久化 I/O。

## 使用示例

```bash
go run ./examples/client-entry
```

预期输出：

```text
player=player-1 generation=1
```

示例的 `exampleHandshake` 直接返回固定测试材料，只用于展示分层与 proof 流程。它不是生产登录协议；公网部署必须使用 TLS 或等价的认证密钥交换，并替换为产品的 Handshake 实现。

## 当前限制

- 仅提供单进程内存 Registry；不提供跨节点、持久化、选主或全局踢人路由。
- 仅提供 TCP 行协议；WebSocket、HTTP、protobuf 和二进制帧可复用 proof 语义，但必须另行冻结线格式。
- `SingleSession` 是唯一内置策略；多端并存、顶号通知和会话查询留给后续业务策略。
- 不提供账号密码、OAuth、平台 SDK、TLS 证书或通用生产 Handshake。
