# 设计原则：把复杂度放回它的 owner

一天，小林提交了一版“万能 Runtime”设计：

```text
Runtime
  ├── CreateBattle
  ├── FindPlayer
  ├── SaveWallet
  ├── ReloadRoom
  └── KickConnection
```

老周看完说：“功能很多，边界没了。”

## 三层，而不是一个万能框架

GSR 分为三层：

```text
Business Layer
  Battle / Room / Player / Wallet
           ↓
Runtime Tooling
  Discovery / Snapshot / Supervisor / Control / Record
           ↓
Core Runtime
  Service / Command / Mailbox / Scheduler / Timer / Cluster
```

依赖只能向下。

Core 不得引用 `game/`、`examples/` 或业务领域类型。Tooling 使用 Core 的公开能力，但不能为了自己方便给 Runtime 增加私有 getter。Business 可以组合 Core 和 Tooling，但权威业务状态仍属于自己的 Service。

## 原则一：状态只经 Command 变化

错误版本：

```go
player.Coins += 100
wallet.Balances[player.ID] += 100
```

两个对象、两个写入口、一次崩溃就可能留下半个结果。

GSR 版本不是“加两把锁”，而是让各自 owner 处理自己的 Command：

```text
Battle Finish
  -> Send CommitSettlement(RequestID)
  -> Wallet pending
  -> LedgerRunner
  -> ApplyLedgerResult
  -> Wallet committed
  -> Send ApplySettlementResult
  -> Battle finished
```

跨 Service 不假装原子事务。每个 owner 保存可恢复的阶段。

## 原则二：Send、Call 和 Reply 保持原语

`Send` 表示调用方只关心是否被接受：

```go
err := runtime.Send(ref, StartCommand, struct{}{})
```

`Call` 表示调用方需要当前结果：

```go
value, err := runtime.Call(ctx, ref, GetSnapshotCommand, struct{}{})
```

Handler 用 `Reply` 返回：

```go
return commandContext.Reply(snapshot)
```

上层不应把它们全部包装成隐式 RPC。BattleContext 和 PlayerContext 只是给插件式业务代码增加领域能力，仍保留 `Self`、`Source`、`Reply`、`Send` 等一致语义。

## 原则三：异步工作必须有 owner

“我开一个 goroutine，做完再改 Service 状态。”

这是 GSR 最明确禁止的写法之一：

```go
func (s *walletService) Handle(...) error {
    go func() {
        result := writeDatabase()
        s.balance += result // Handler 外写状态
    }()
    return nil
}
```

正确结构：

```text
WalletService Handler
  -> 有界 LedgerRunner.Submit
  -> 外部 I/O
  -> Runtime.Send(private result Command)
  -> WalletService Handler 更新状态
```

`LedgerRunner` 由组合根创建，是 Runtime-owned Core Runner 的领域适配器。Core 统一关闭并等待真实 worker 返回；processor 不能保存 CommandContext，也不能直接修改 Wallet。

## 原则四：超时是观察，不是撤销

```go
ctx, cancel := context.WithTimeout(context.Background(), time.Second)
defer cancel()
result, err := runtime.Call(ctx, wallet, CommitCommand, request)
```

如果返回超时，只能得出：

```text
调用方在截止时间前没有拿到结果
```

不能得出：

```text
目标没有执行
```

因此资金、匹配、创建、Drain 等流程必须使用 `RequestID`。重试时查询原请求状态，而不是假设第一次没有发生。

## 原则五：旧 Ref 不复活

Service 结束后，旧 `ServiceRef` 永久失效。Snapshot 恢复、Supervisor 重启、人工补偿都会创建新实例和新 Ref。

```text
old Ref --X--> stopped
snapshot -> create -> new Ref
```

这让缓存旧地址的错误变得可见，也让 Drain 和版本发布可以被审计。

## 原则六：观测与控制分开

`Runtime.Inspect()` 只返回副本。Monitor 只转换副本。Observer 记录 observed state。

改变系统需要另一条明确路径：

```text
Principal + RequestID
  -> Coordinator
  -> NodeAgent receipt
  -> 外部 Runner
  -> Runtime.Stop / CreateService
  -> result Command
```

看见系统的人，不自动获得改变系统的权限。

## 原则七：先测量，再优化

没有数据时，不引入 Ring Buffer、对象池或 Timer Wheel。

先回答：

- Send、Call、Timer 各是多少？
- Mailbox p95/p99 等待多久？
- 单 Battle 和多 Battle 差多少？
- 每次操作分配多少？
- 广播人数增长后发生什么？

如果热点来自一个 Battle 的复杂 Handler，增加 Worker 不会让同一个 owner 并行。应先缩短 Handler，隔离慢 I/O，再考虑拆分权威状态。

## 一张评审清单

设计一个新模块时，依次问：

1. 它属于 Core、Tooling 还是 Business？
2. 权威状态由谁拥有？
3. 写入口是否只有 Command？
4. 是否错误地持有另一个 Service 指针？
5. 异步任务由谁关闭并等待？
6. 超时后如何查询未知结果？
7. Stop、Close、panic 和迟到消息如何处理？
8. 测试保护的是单包行为还是跨包场景？

后面的每一章，都会把这张清单落实到一段具体源码上。
