# 前言：先让一局游戏跑起来

小林第一次接手游戏服务器时，桌上放着三张需求单：

- 玩家登录后进入房间；
- 房间创建一局战斗；
- 战斗结束后给玩家增加金币。

“这不就是三个对象互相调用吗？”小林问。

老周没有回答，而是在白板上补了几行字：

```text
玩家断线重连
战斗定时事件迟到
结算请求超时但数据库已经成功
节点准备热更新
服务正在关闭，消息同时到达
```

“现在还是三个对象吗？”

这本书就从这个问题开始。

## 这本书讲什么

GSR 是 Game Service Runtime 的缩写。它借鉴 Skynet 的几个朴素思想：

- 用可寻址的 Service 表达长期运行的状态 owner；
- Service 之间只传地址和消息；
- 上层服务按职责组合，不让 Runtime 理解 Battle、Player 或 Wallet。

GSR 同时接受 Go 带来的现实：

- goroutine 不能被安全强杀；
- 超时不等于函数已经停止；
- 生命周期必须有明确 owner；
- 同一份业务状态需要一个可证明的串行入口。

因此，GSR 不是“把 Skynet API 翻译成 Go”，也不是通用 Actor 框架。它是一套围绕 `Service`、`ServiceRef`、`Command`、`Send`、`Call`、Mailbox 和显式生命周期建立的游戏服务器 Runtime。

## 全书的故事

我们会反复使用同一条业务链：

```text
客户端
  -> Login / Gateway
  -> PlayerService
  -> RoomService
  -> BattleService
  -> WalletService
  -> LedgerStore
```

在这条链上，Alice 登录、进入房间、开始打地鼠、命中目标并获得金币。随后运维人员观察节点、切换 ServiceSet、Drain 旧实例、停止节点，最后在隔离环境中 Replay 一局战斗。

每一章都尽量回答六个问题：

1. 开发者遇到了什么真实问题？
2. 最直接的写法为什么会失败？
3. 谁拥有这份状态？
4. Command 从哪里进入，结果如何返回？
5. 失败、超时和关闭时发生什么？
6. 对应源码和测试在哪里？

## 阅读方式

第一次接触 GSR，建议依次阅读：

## 先运行一个例子

在仓库根目录执行：

```bash
go run ./examples/local-runtime
go run ./examples/whackmole
```

第二条命令会输出一次成功的 Kick：

```text
whackmole kick: main.KickResult{Hit:true, Score:1, Reason:""}
```

这行输出背后已经经过：

```text
Runtime.Send(Start)
  -> Battle Mailbox
  -> BattleLogic
  -> Timeline
Runtime.Call(Kick)
  -> CommandContext.Reply
  -> Pending Call
  -> 调用方
```

本书会把这条链逐层拆开，再重新组合起来。

## 契约从哪里来

本书是教程，不是第二份 API 契约。

- `docs/rfcs/` 定义公开语义；
- `docs/DECISIONS.md` 帮助检索“为什么”；
- 源码和测试展示当前实现；
- 本书负责把它们讲成一条可以学习的路径。

如果本书和 RFC 冲突，以 RFC 为准，并应修正文稿。阅读 RFC 的入口是仓库的 `docs/SUMMARY.md`。

## 对“性能”的预告

GSR 选择 Mailbox 串行，不代表所有游戏只用一个线程。它表示：

```text
同一个 Battle 串行
不同 Battle 可以并行
同一个 Player 串行
不同 Player 可以并行
```

当前 Apple M2 上，打地鼠轻量 Kick 路径大约是微秒级，每次仍有十余次内存分配。这个数字只是定位热点的起点，不是生产容量承诺。真正的服务器还要测 p95/p99、网络、广播、Timer、持久化和队列等待。
