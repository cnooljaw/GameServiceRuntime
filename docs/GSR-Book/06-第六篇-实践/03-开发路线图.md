# 开发路线图：已经有什么，还缺什么

路线图的权威来源是 `docs/rfcs/RFC-0500-Roadmap.md`。本章只给阅读者一张面向源码的地图。

## 已实现纵向

### Core Runtime

```text
Service / ServiceRef / Command
Send / Call / Reply / Pending Call
Mailbox / Scheduler / Timer
Lifecycle / Task tracking
Cluster Data Plane / TCP
Runtime Inspection
```

### Tooling


### Business

```text

Room

```

## 当前工程待办

以 `docs/TODO.md` 为准，重要开放项包括：

- 固定机器上的业务性能基线；
- 单 Battle、多 Battle、不同广播人数的 p50/p95/p99；
- Mailbox 拒绝与队列等待；
- 用数据决定是否优化分配、批处理或 owner 边界。

## 当前明确不承诺

GSR 目前不是完整生产平台，不内置：

- 通用数据库和 ORM；
- Gossip Discovery；
- 自动选主；
- 全自动 Reconcile Controller；
- 跨进程持久控制操作；
- 生产级 TLS/账号系统；
- 通用协议网关；
- 自动扩缩容和放置调度；
- 账本数据库 adapter；
- Web 管理台；
- 完整游戏业务框架。

这些能力可以建立在现有边界上，但需要新的 RFC、owner 和验收。

## 下一步怎么选

如果目标是验证真实游戏：

```text
生产 ProtocolMapper
  -> Player/Room Factory
  -> 真实 LedgerStore
  -> 场景压测
```

如果目标是运维：

```text
持久操作 Store
  -> 外部认证管理入口
  -> Desired State Controller
  -> Reconcile
```

如果目标是性能：

```text
固定环境 benchmark
  -> trace/profile
  -> p99 与 queue metrics
  -> 局部优化 RFC
```

如果目标是可靠重放：

```text
稳定业务 Codec
  -> Redactor
  -> 持久 Archive
  -> 随机/时间/外部 Effect 隔离
```

## 不要跳过的问题

进入任何后续阶段前，先回答：

- 新状态归谁？
- 新任务由谁 Close？
- 超时后如何 Resolve？
- 旧 Ref 如何 fencing？
- 新 API 属于 Core、Tooling 还是 Business？
- 哪个真实场景证明它必要？

## 本章小结

路线图不是功能愿望清单，而是复杂度进入系统的顺序。GSR 选择先冻结可验证的边界，再逐层增加能力；每一步都应能由源码、测试和文档共同证明。
